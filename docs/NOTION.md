# Notionの設定と復旧

このチャットのNotion接続は読み取り確認にだけ使用しました。アプリには別の長期Notion API接続が必要です。自動テストは独立したデータで実行します。v0.5では、依頼された実WS本文へ②③④の記録を初期化しました。詳細は [本文同期仕様](SPEC-v0.5.md) を参照してください。

## 初回設定

1. Notionの内部インテグレーション等、運用で認可されたサーバー用API資格情報を用意します。
2. WS一覧と各WSページをその接続に共有し、必要な読取り・作成・更新・ファイル添付の権限を付与します。
3. `.env` の `NOTION_TOKEN` と `NOTION_WORKSHOPS_SOURCE` を設定します。後者はDBを内包するコンテナーIDではなく、WS一覧の**data_source ID**です。`collection://` 接頭辞は除去しUUIDを指定します。
4. 専用検証DBで同期・WS作成・子DB作成・メンバー更新・競合・成果保存を確認してから、本番のデータソースに切り替えます。

この実装のHTTPは `https://api.notion.com/v1`、`Notion-Version: 2026-03-11` に固定しています。サーバーのみから呼び出します。[Notion API](https://developers.notion.com/reference/intro)、[DB作成](https://developers.notion.com/reference/create-a-database)、[データソース作成](https://developers.notion.com/reference/create-a-data-source)、[File Upload](https://developers.notion.com/reference/file-upload)

### 内部接続の作成とトークン入力

1. [NotionのDeveloper portal](https://app.notion.com/developers/connections)を開き、「Internal connections」から新しい内部接続を作成します。接続名は `アイディアワークショップ支援ツール`、対象はWS一覧を持つワークスペースです。ワークスペースオーナーによる操作が必要です。
2. 内容の読取り・更新・挿入を許可します。参加者メールはDBのtitle欄から読むため、Notionの全ユーザー情報を取得する権限は不要です。
3. 「Content access」でWS一覧の親ページを指定するか、親ページの「…」→「接続」→「接続を追加」で、この内部接続を選びます。必要なWSページと子参加者DBへのアクセスを確認します。
4. 「Configuration」でAPIトークンを取得し、ローカルの `.env` の `NOTION_TOKEN=` に保存します。チャットや公開リポジトリへ貼り付けません。非表示入力を使う場合は、リポジトリのPowerShellで `& .\scripts\set-notion-token.ps1` を実行します。

読取りだけで接続を確認するコマンド：

```sh
node --env-file=.env scripts/check-notion.js
```

このコマンドはWS一覧と各子参加者DBのスキーマ／読取りを調べ、一時的なメモリーDBだけを使います。Notionへ書き込まず、稼働DBの権限も変更しません。接続確認後に通常サーバーを再起動すると同期が始まります。内部接続を作成しただけではページへのアクセスがなく、親ページの共有操作も必要です。[Notion公式：内部接続](https://developers.notion.com/guides/connections-and-tokens/internal-connections)

一覧が空で設定歯車がない場合は、Notion上の参加者権限をまだ読めていない可能性があります。公開Webへの移動だけでは接続資格情報の欠落は解消しません。アプリは未接続・同期待ち・同期失敗を区別して表示し、接続回復後はログイン中でも一覧と管理者属性を再取得します。未接続状態を固定の管理者権限やチャットの接続結果で代用しません。

## WS一覧のスキーマ

| プロパティ名 | 型     | 値                                                 |
| ------------ | ------ | -------------------------------------------------- |
| 名前         | title  | WS名                                               |
| 終了日       | date   | 日付または日時。範囲ならend側を期限とする          |
| ステータス   | status | 未着手、進行中、完了（変更不可）、破棄（閲覧不可） |

この型と実値は2026-11-03に接続ツールで読み取り確認済みです。ワークスペース／ページのIDや参加者メールは公開リポジトリには記録していません。

## Notion側で追加するときのテンプレート

WS一覧DBに「標準ワークショップ」テンプレートを手動で作成し、次を含めてください。本番テンプレートの作成・スキーマ変更はこの開発では行っていません。

- ステータス初期値は「未着手」または運用に応じ「進行中」。期限を入力する。
- 行ページの直接の子にインラインDBを1つだけ置き、タイトルを正確に「参加者一覧」にする。
- 子DBのスキーマを以下に揃え、テンプレートに実際の参加者やOTP履歴は保存しない。

| 名前        | 型     | 内容                                         |
| ----------- | ------ | -------------------------------------------- |
| 名前        | title  | 小文字に正規化したメール。WS内で重複不可     |
| 選択        | select | 管理者、編集者、閲覧者                       |
| グループ    | select | A班・B班等。空欄は未割当                     |
| OTP認証結果 | select | 認証済（参照認証には使用しない）             |
| OTP認証日時 | date   | 任意の参考履歴（アプリから自動書込みしない） |

アプリの「このWSをNotionへ接続」はWSページとこの子DBを自動生成します。APIでstatus型の定義を生成することは行わず、既存のWS一覧スキーマを検証して使います。Notionが未設定の間はサーバーだけで管理し、後からWSごとに接続できます。

## 同期と権限

WS一覧は30秒ごとにページングして読取り、子DBも全ページを読みます。ページIDと子データソースIDで対応付けます。グループ名を内部チームIDに紐付け、既存チームを再利用します。グループ名の変更は新しいチーム扱いになるため、既存マップ・デッキ・議論は旧チームに保持されます。既存成果を移行する前にグループ名を変更しないでください。

WSのname／status／endDateは双方向です。アプリ側変更はdirtyとしてSQLiteに永続化。Notionの`last_edited_time`が基準と異なれば競合にし、管理者設定でNotion側またはアプリ側の採用を選びます。Notionに比較更新APIがないため、読取りと書込みの間のごく短い変更は原子的には防げません。運用では同じWSのマスタを両側で同時変更しないでください。複雑な並行運用では、更新リビジョン用NotionプロパティやWebhook／キューの追加を検討してください。

参加者はNotion優先で毎回置き換えます。アプリからの参加者変更は先にNotionへ書き、再読取りに成功した内容だけを権限に使用します。削除された参加者は既存CookieがあってもWSへアクセスできなくなります。Notion由来の管理者権限も毎要求の再計算対象です。ブートストラップ管理者のみサーバー設定の復旧用権限を維持します。

同期失敗・型違い・重複・競合・権限情報が60秒以上古い場合は、そのWSの参加者アクセスを止めます。サーバー設定の初期管理者が修正できます。終了日超過後のローカル破棄は直ちに適用し、Notionへの反映が失敗しても参加者の閲覧を再開しません。Notionへは次の成功した同期で反映します。

WS削除はアプリで論理削除し、Notionではarchiveへ送ります。管理者のローカル記録は保持されます。Notion側でarchiveされたページも再確認して参加者閲覧を止めます。接続自体が失われた場合もアクセスを許可しません。

## 作成要求の応答が不明になった場合

外部APIは完全な冪等作成を保証しないため、新規WSページの作成要求前に`createAttempt`を保存します。失敗後の自動再送は行いません。

1. 管理者はNotionでWS名とページ内の `Workshop Idea Deck ID: <ローカルWSのUUID>` を確認する。
2. サーバー停止後にSQLiteをバックアップする。
3. 作成済みなら、運用者がその安定ページIDを対応させる。未作成を確認できた場合のみ、該当WSの`createAttempt`を解除して再試行する。開発時に本番DBへ直接SQLを実行しない。
4. 子DBの作成応答だけ不明なら、次回は子DBを再探索する。存在しなければ`childCreateAttempt`を保持して止める。重複DBがある場合は一意に整えてから復旧する。
5. 復旧後に「今すぐ同期」でメンバー・状態・期限・チームを照合する。

これは運用者向けの復旧手順です。応答不明状態を自動的に成功扱いしたり、確認なくロックを解除するAPIはありません。

## 成果保存

完了WSの管理者が明示実行すると、WSページの子に「チーム名 成果 rリビジョン」ページを作成します。Markdown相当の文章を段落に分割し、生成済みPNGはNotion File Upload経由で添付します。同名の成果ページが既にあれば再利用します。成果が大きすぎる場合はMarkdownのダウンロードを案内し、元データはSQLiteに保持します。

ライブ共同編集内容そのものを毎回Notionへ転記する構成ではありません。Notionはマスタと完了成果、SQLiteは進行中の作業状態です。
