# v0.5 Notion本文と各ステップの同期

2026-11-03の追加依頼を反映します。従来の「NotionはWSと参加者、SQLiteは作業内容だけ」という分担を変更し、ワークショップ本文にも作業内容を同期します。

## ①の階層

WSページの参加者一覧と同じページで、通常の見出し「① もやもやの言語化（N1）」から次の②見出しまでを読みます。

| Notion        | マップ                                 |
| ------------- | -------------------------------------- |
| トグル見出し2 | メイントピック（中心の右の最初の階層） |
| トグル見出し3 | その子                                 |
| トグル見出し4 | さらにその子                           |
| トグル        | 以後の階層                             |

箇条書き等の文字も子として取り込み、サンプル内の情報を省略しません。ブロックIDとアプリの論理IDを対応付け、再同期で同じ項目を増やしません。論理ID対応表を②にも保存し、新しいローカルDBからの復元時もカードとデッキの関係を保ちます。

班の区切りがない既存サンプルはA班（A班がない場合は先頭の班）へ取り込みます。他の班は①配下の「チーム：B班」等のトグル内に、同じ見出し2→3→4→トグルの構造を作ります。従来どおり他班は閲覧専用です。

## 起動・編集と競合

- 起動時にNotionを読み、マップへ反映します。既存のローカル内容は初回取り込み前にバックアップします。Notionにない古いマップを自動でマスターへ書き足しません。
- Notion側の変更は通常30秒間隔の同期で取り込みます。ページ更新時刻が変わらなくても少なくとも60秒間隔で本文を再確認します。管理者の「Notionから再読込み」で即時取得できます。
- アプリの操作時はNotionへの保存を開始し、文字更新・追加・接続変更・削除を反映します。単純な編集は対象ブロックと該当ステップ記録を照合します。構造の変更はツリー全体を読み直します。
- Notion側の更新を検知したら、古いアプリ内容で上書きせず409を返して取り込みます。Notion APIには全ブロックの条件付き一括更新がないため、確認と書込みの間に発生する完全な同時編集を原子的に保証するものではありません。
- APIでは既存ブロックを別の親へ移動できないため、枝の移動は新しい位置へ子孫を含めて作成し、作成を確認後に元のブロックをTrashへ移します。アプリの論理IDは維持します。画像等を含む未対応の枝の構造変更は、内容を失わないよう停止してNotion側での操作を案内します。
- Notionへ届かなかった場合もアプリ側の入力を保存し、「Notion同期未完了」を表示します。追加・更新・削除の処理履歴を保存し、応答消失時は読み返して照合します。結果不明の追加を盲目的に再送しません。
- 「同期を再試行」で継続できます。管理者がNotionを採用して再読込みする場合は、未同期ローカル内容を先に別のバックアップへ保存します。

## ②③④

見出しを以下へ変更します。

1. ② 言語化の絞込み（カードの選択）
2. ③ アイデアの可視化（カードの可視化）
3. ④ アイデアの絞込み（投票）

各見出し配下に「チーム：A班」等のトグルを置き、人が読める要約と、復元用JSONのcodeブロックを記録します。JSONのcaption `Workshop Idea Deck state v1` は対応付けに使うため保持してください。

| ステップ | 保存する内容                                                                 | Notion編集から反映する項目                                         |
| -------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| ②        | カードID・NotionブロックID・本文・色、合計票、デッキID、中心の表題、票数上限 | `totals`、`deck`、`rootText`。トピック本文は①がマスター            |
| ③        | デッキ、議論のWHAT/WHO/HOW・論点・キーワード・記録・履歴・進行状態、生成画像 | `discussion`。画像はNotionへ直接アップロードされた16:9 PNGを読込み |
| ④        | アイデアの合計票と票数上限                                                   | `totalVotes`                                                       |

①のマップと②③④の記録は、アプリで操作した同じ処理内で同期します。既存の完了時の成果保存も継続します。画像はNotionのFile Upload APIで添付し、キーが同じ画像を再添付しません。

**個人別の票とログインメールは記録に書き出しません。** 合計票をNotion側から変更したときは、該当対象の個人票をクリアし、匿名の初期票として採用します。その後のアプリ投票を足すため、読み直しても二重集計しません。投票上限等の管理設定はアプリ管理画面から変更します。

JSONは型・件数・文字数を検証します。不正なJSONは、その同期全体を適用せずエラーにします。本文・ID・集計の破損を避けるため、マップは班ごとに500項目、記録JSONは16万文字以内、議論履歴は100回以内です。

## 運用・実接続確認

`scripts/check-notion-content.js`はアプリを停止してから実行する運用者用です。既定はNotionの読取りのみで、稼働DBの取り込み状態は更新します。`--initialize`は②③④の記録を作成します。`--roundtrip`は一時トピックを実際に追加・編集・削除するため、対象環境で明示的な許可を得た場合だけ実行します。往復テストでは`--page=対象ページID --team=A班`で対象を指定します。`--resume-roundtrip`は更新済みの一時トピックが一意に見つかった場合だけ、その同じトピックの削除確認を再開し、新しいトピックを追加しません。

今回の環境ではSQLiteの整合バックアップ後に、指定サンプル55項目を読み取り、②③④に3班ずつ9件を初期記録しました。元の①のブロックID・本文・階層のハッシュ一致を確認しています。トピックの追加・編集・削除は独立した自動テストで検証済みです。その後、利用者の個別許可を得て、A班の一時トピック1件の追加・文字更新・削除を実APIで検証しました。最終読取りで一時トピックが残っていないこと、既存55項目の論理IDと階層を保持したことを確認しました。テスト中のNotion側の表題変更1件も最新原文に合わせて取り込まれています。

APIは`2026-03-11`。参考：[ブロックと見出し4](https://developers.notion.com/reference/block)、[子ブロック追加と配置](https://developers.notion.com/reference/patch-block-children)、[ブロック更新](https://developers.notion.com/reference/update-a-block)。
